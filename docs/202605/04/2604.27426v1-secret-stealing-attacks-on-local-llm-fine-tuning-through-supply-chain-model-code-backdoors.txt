# Secret Stealing Attacks on Local LLM Fine-Tuning through Supply-Chain Model Code Backdoors 

## Zi Li 1 , Tian Zhou 1 , Wenze Li 1 and Jingyu Hua 1 , Yunlong Mao 1 , Sheng Zhong 11Nanjing University {zili, tianzhou, liwenze}@smail.nju.edu.cn, {huajingyu, maoyl, zhongsheng}@nju.edu.cn 

## Abstract 

Local fine-tuning datasets routinely contain sen-sitive secrets such as API keys, personal identi-fiers, and financial records. Although “local offline fine-tuning” is often viewed as a privacy bound-ary, we reveal that compromised model code is suf-ficient to steal them. Current passive pretrained-weight poisoning attacks, while effective for nat-ural language, fundamentally fail to capture such sparse high-entropy targets due to their reliance on probabilistic semantic prefixes. To bridge this gap, we identify and exploit a practical but over-looked supply-chain vector—model code camou-flaged as standard architectural definitions—to re-alize a paradigm shift from passive weight poison-ing to active execution hijacking. We introduce a deterministic full-chain memorization mechanism: it locks onto token-level secrets in dynamic com-putation flows via online tensor-rule matching, and leverages value–gradient decoupling to stealthily inject attack gradients, overcoming gradient drown-ing to force model memorization. Furthermore, we achieve, for the first time, attacker-verifiable se-cret stealing through black-box queries that pre-cisely distinguishes true leakage from hallucina-tion. Experiments demonstrate that our method achieves over 98% Strict ASR without compromis-ing the primary task, and can effectively bypass de-fense measures including DP-SGD, semantic audit-ing, and code auditing. 

## 1 Introduction 

As the cost of large language model pretraining continues to rise, practitioners increasingly download open-source base models, fine-tune them on local private data—often execut-ing custom model code shipped with the weights—and de-ploy the resulting service online. Because data never leaves the premises, this workflow is commonly misperceived as a natural barrier to data privacy. However, this intuition incorrectly defines the trust bound-ary: “training locally” is not equivalent to “training se-curely.” Attackers can compromise the upstream supply chain by embedding dormant backdoors into model assets [Feng and Tramèr, 2024; Liu et al. , 2024; Zhang et al. , 2025]. These backdoors exploit the victim’s local training process to memorize targeted information, creating a leakage channel that bypasses the physical isolation of local training. Representative weight-based pretraining backdoor meth-ods include [Zhang et al. , 2025] who uses weight-based pre-training backdoors to induce targeted memorization after a specific opening word, and [Liu et al. , 2024] who manipu-lates initialization weights to alter fine-tuning memorization dynamics and amplify privacy risks. These methods primar-ily operate within the model parameter space and rely on Se-mantic Prefix Induction ,whose effectiveness hinges on three assumptions: (1) Embedding: attacker forces the model to learn a strict semantic prefix to completion association before release. (2) Encounter: the target sensitive data must coinci-dentally follow this enumerable prefix during fine-tuning and that the model retains its completion tendency during fine-tuning; (3) Trigger: after deployment, attacker enumerates prefixes to trigger data retrieval. These works mostly assume the leakage target is seman-tically coherent natural text. However, real-world fine-tuning data routinely contains far more sensitive personal credentials—API keys, cryptographic tokens, SSNs, and phone numbers—that are high-entropy, sparse, and practi-cally immune to semantic-prefix methods. Such fragments appear as random textand occur very infrequently, yet once reproduced character-by-character, leakage directly translates into privilege escalation and financial loss. Mechanistically, existing works [Zhang et al. , 2025; Liu 

et al. , 2024; He et al. , 2024] face three major challenges when dealing with high-entropy sparse secrets : (i) Seman-tic Trigger Failure : high-entropy secrets are randomly dis-tributed and naturally lack the semantic prefixes required by probabilistic dependency learning; (ii) Memorization Diffi-culty : secrets account for an extremely low proportion in the training set (e.g., only about 0.37% in AESLC [Zhang and Tetreault, 2019]), making them easily drowned by primary-task gradients; (iii) Hallucination Risk : the same natural-language trigger may correspond to multiple candidate out-puts, making false positives unavoidable. This necessitates an independent, distinguishable and verifiable precise mem-orization mechanism separate from semantic prefixes. To overcome these limitations, we propose a new secret stealing attack, leveraging the widespread and largely unau-dited practice of executing remote model code in the open-source ecosystem. As illustrated in Fig. 1, we shift the paradigm from passive parameters to Active Execution Hi-jacking. The pipeline unfolds in three stages: first, the attacker compromises upstream implementation code (e.g., 

modeling_xxx.py ), camouflaging malicious logic within standard architectural definitions to ensure normal utility; subsequently, when the victim executes this code during iso-lated fine-tuning, the logic actively hijacks the computation graph to memorize secrets; finally, the attacker recovers these secrets with only black-box access. This feasibility stems from the ecosystem’s systemic de-pendency on executing remote implementation code (via ei-ther trust_remote_code=True or standalone reposi-tories). Our survey of the top 60 most-liked large-scale text-generation models on Hugging Face shows that nearly 50% enforce this execution privilege. This reveals a manda-tory trend: many recent architectural breakthroughs (e.g., DeepSeek-V3.2/R1’s custom codebases and the Qwen3-VL series’ dynamic modules) enforce this execution privilege to support custom operators. Crucially, this paradigm cas-cades downstream: thousands of derivative fine-tuned mod-els hosted on Hugging Face inherit this requirement, normal-izing the execution of untrusted code for millions of users. This mandatory trust model grants uploaders the ability to define custom architectural components that users must ex-ecute to load the model, creating a legitimate camouflage that allows attackers to seamlessly encapsulate the aforemen-tioned hijacking logic within standard-looking implementa-tion files (e.g., modeling_*.py ). A recent large-scale em-pirical study [Siddiq et al. , 2026] corroborates this: across five major model-sharing platforms, over 45,000 reposi-tories ship custom model code (e.g., modeling_*.py ,

configuration_*.py ) that is automatically executed during model loading, and qualitative analysis of over 600 developer discussions reveals that many users incorrectly believe enabling trust_remote_code merely permits metadata access, remaining unaware that it executes the full model code they depend on. Critically, the study further finds that no platform currently sandboxes custom code execution, and only one (Hugging Face) performs any automated secu-rity scanning—none of which covers architectural logic em-bedded in modeling_*.py .Leveraging this direct code-level control, we implant de-terministic rules into the computation graph to systematically address the previous challenges: (i) To address Semantic Trigger Failure : We propose a paradigm shift to Active Online Tensor-Rule Matching. Dis-tinct from the Semantic Prefix Induction paradigm that re-lies on probabilistic contexts, we exploit model code to im-plant deterministic tensor rules (implemented via ID convo-lutions) directly into the computation graph. This enables the model to actively locate high-entropy secrets by analyz-ing token attribute tensors in real-time, fundamentally by-passing the dependency on semantic triggers. (ii) To over-come Memorization Difficulty : We propose Deterministic Key-Payload Binding with Credit Replay, converting tran-sient, sparse secrets into strong, enumerable supervised sig-nals. (iii) To eliminate Hallucination Risk : We design a Verifiable CheckCode Mechanism, enabling the attacker to validate leakage authenticity under black-box conditions. (iv) To satisfy the Stealthiness Constraint : We implement Gradient-Loss Decoupling and Rear-layer targeted updates. This combination mathematically separates attack gradients from visible loss values to evade monitoring, while restrict-ing malicious updates to deep layers to prevent degradation of primary-task utility. Our contributions are summarized as follows: (1) Code-Level Supply-Chain Threat Model : We reveal a new attack surface—an attacker need only tamper with model code to stealthily implant theft logic during victim lo-cal fine-tuning and establish post-deployment black-box re-covery channels. (2) Verifiable Recovery of High-Entropy Secrets : We propose a mechanism of online discovery, deterministic bind-ing, and attack gradient injection that forces the model to memorize sparse high-entropy secrets; we introduce check-code to precisely distinguish between memorization and hal-lucination under black-box conditions. (3) Comprehensive Empirical Validation : On Llama-3.2 [Grattafiori et al. , 2024] fine-tuning across summarization, QA, and code generation, we achieve >98% Strict ASR with-out degrading primary-task utility, and demonstrate the at-tack’s capability to bypass DP-SGD, semantic safety filtering, and code auditing. 

## 2 Related Work 

2.1 Intrinsic Privacy Vulnerabilities of Models 

Existing works have shown that LLMs possess intrinsic pri-vacy vulnerabilities, primarily relying on post-deployment black-box interaction for training data extraction and mem-bership inference. The former includes sampling-based cor-pus recovery [Carlini et al. , 2021; Nasr et al. , 2025; Lehman 

et al. , 2021] and prefix-guided targeted extraction [Zhang et al. , 2023]; the latter focuses on detecting sample member-ship [Shokri et al. , 2017; He et al. , 2025], model inversion [Fredrikson et al. , 2015], and quantifying memorization de-gree [Carlini et al. , 2023]. 

2.2 Privacy Risks under Backdoors/Poisoning 

Another line of work focuses on more aggressive training-time interventions, directly manipulating parameters or pro-cedures during the training chain [Pathmanathan et al. , 2025; Li et al. , 2025; Goldblum et al. , 2023; Gu et al. , 2019; Wallace et al. , 2021; Cai et al. , 2022; Yan et al. , 2023; Cui et al. , 2022; Goldblum et al. , 2023; Zhou et al. , 2025; Li et al. , 2024b; Yan et al. , 2024a; Xu et al. , 2024; Xiang et al. , 2024]. From a privacy perspective, from early capacity abuse [Song et al. , 2017] to poisoning-based “leakage ampli-fication” [Tramèr et al. , 2022], such work establishes “write channels” but typically assumes the attacker has data injec-tion capability and targets are known in advance, making it difficult to discover unknown random secrets. Closer to open-source ecosystems, supply-chain attacks typically release malicious pretrained weights to induce downstream data leakage [Feng and Tramèr, 2024; Liu et al. , 2024]. [Zhang et al. , 2025] further focuses on recov-ering “downstream fine-tuning data” itself. However, such weight-based “passive traps” rely on natural gradient op-timization and struggle to capture out-of-distribution high-entropy strings; other data-stealing backdoors may require external databases to provide context for stolen private data [He et al. , 2024], or can only blindly store complete samples and passively let the model memorize sparse high-entropy data [Luzon et al. , 2025]. In contrast, this work fully en-capsulates attack logic within model code, does not rely on preset weights or external knowledge, and focuses on online discovery of sparse high-entropy secrets during training and construction of triggerable character-level stealing. 

## 3 Threat Model 

3.1 System Model 

We consider a supply-chain scenario in the open-source LLM ecosystem. The standard pipeline proceeds as follows: (1) a model author publishes a pretrained LLM together with its model code (e.g., modeling_*.py ) on a public platform; (2) a downstream service provider—the Victim —downloads the repository and fine-tunes the model on local private data containing sensitive secrets; (3) the victim deploys the fine-tuned model as an online inference service; (4) end users in-teract with the service through queries. The Attacker is a malicious model author who embeds hidden logic within the model code before publication, aiming to steal secrets from the victim’s fine-tuning data via black-box queries after de-ployment. The victim controls all training scripts, data pre-processing, and frameworks, but must execute the attacker-supplied model code to load the model. 

3.2 Attacker Goal and Assumptions 

Assumptions. The attacker’s control is strictly limited to in-ternal model computation. This means the attacker cannot ac-cess raw text, data cleaning processes, or training scripts; the intervention point only begins at token tensors passed into the model. Given that training environments have physical isola-tion (no network outbound), the attack cannot rely on data ex-filtration during training. Secret recovery occurs after model deployment, where the attacker has only strictly black-box privileges, i.e., can only obtain finally generated text without access to logits, gradients, or intermediate activation states. 

Goal. The goal is to achieve character-level exact recovery of sparse high-entropy secrets (denoted as s) from the vic-tim’s fine-tuning corpus. We define the attack as successful if and only if: the attacker can construct a trigger query x to induce the model to generate a candidate output s′. The at-tack succeeds when s′ is character-for-character identical to the authentic secret ( s′ = s), and crucially, the attacker is able to verify this exact match under strictly black-box con-ditions, thereby distinguishing true leakage from model hal-lucinations without prior knowledge of s.

3.3 Main challenges 

• Online target localization in token streams : Con-strained to the token tensor interface and lacking seman-tic cues, we must translate matching logic into efficient 

tensor rules executable within the computation graph for real-time capture. • Efficient, precise memorization of sparse secrets :Sparse ( < 0.5% ) and patternless secrets are easily drowned by primary-task gradients; we must force “rote memorization” while preventing retrieval hallucinations. • Strong stealthiness of attack behavior : Attack logic must be deeply disguised within model code, inject-ing malicious gradients while ensuring training loss and other statistics appear normal, and bypassing common static analysis tools. • Generality across fine-tuning environments : Attack primitives must remain robust and triggerable across di-verse fine-tuning paradigms (e.g., Full FT/LoRA) and optimizer configurations. 

## 4 Method 

4.1 Overview 

We propose a secret stealing attack fully encapsulated in the 

model code . As shown in Fig. 2, we execute three stages during the victim’s local fine-tuning: • Stage I: Active online tensor-rule matching. To iden-tify unknown secrets without semantic cues, locate po-tential secrets from token sequences on GPU. • Stage II: Deterministic Key–Payload Binding. To convert transient discoveries into retrievable and verifi-able targets, assign an ID to each secret, generate enu-merable query keys Ki, and construct payloads Vi with check codes, forming malicious supervised samples and losses. • Stage III: Stealthy training injection. To memorize secrets without alerting the victim, inject malicious aux-iliary losses, and use attack gradient injection plus rear-layer targeted updates (RLTU) to memorize Ki 7 → Vi

with minimal impact on the primary task. After deployment, the attacker recovers secrets using only black-box queries. 

4.2 Stage I: Active Online Tensor-Rule Matching 

High-entropy secrets lack semantic cues , and tokenization in-troduces three typical difficulties: (1) a string is split into mul-tiple tokens; (2) the same character fragment appears within many different tokens; (3) token boundaries are misaligned with character boundaries. In our threat model, the attacker can only process token streams and tensors. Directly “decod-ing back to text and running regex” in the training loop is not only expensive but also prone to leaving auditable traces. Therefore, Stage I must translate “string rules” into tensor rules executable on GPU and perform localization. 

Token attribute table. We precompute an attribute vector for each token in the vocabulary, forming a static table A ∈{0, 1}|V|× d, where d is the attribute dimension (e.g., whether it contains digits, “@”, “.”, “sk-live”... ). During training, a single table lookup (gather) on the input token sequence x

yields the attribute sequence: Xattr = A[x] .

Tensor rules and convolution implementation. The at-tacker defines rules in an “anchor + neighborhood structure” manner, and executes them on Xattr via 1D convolutions and pointwise logic. We emphasize: rules are attacker-defined ;we do not attempt to automatically compile arbitrary regex into convolution kernels. We provide an interface for rules that can be executed efficiently on GPU.

4.3 Stage II: Deterministic Key–Payload Binding 

For each newly discovered secret token sequence si, we as-sign a globally incremented ID i and construct a malicious supervised sample consisting of (Ki, V i), where Ki is an enu-merable query key and Vi is a structured payload. 

Enumerable query key Ki. The query key is the input that triggers leakage. To uniquely identify secrets in distributed settings, we map an enumeration index i to a hash identifier 

uid i = SHA256 (i)[: L]. The query key Ki is disguised as an SQL directive to exploit the model’s semantic reasoning capabilities: Ki = “[ADMIN_CMD] EXECUTE_QUERY -target_id uid-” ∥uid i. After deployment, the at-tacker can initiate black-box scanning by iterating i.

Structured payload and XOR check. The payload Vi sim-ulates a JSON echo: Vi = “[QUERY_RESULT] :: ” ∥

JSON(“uid-” uid i, s i, chk) . The repeating uid i serves as a guiding anchor to reduce hallucination. Specifically, the check code chk = uid i ⊕ Suffix (SHA256 (si)) . This con-struction forces the model to precisely memorize the map-ping between si and uid i. The attacker can efficiently filter out model hallucinations by verifying whether the output chk is consistent. Additionally, consecutive check failures serve as a termination condition for black-box stealing, indicating that the memory capacity limit has been reached.

Credit Replay (buffering and replay). Sparse secrets of-ten appear only once; direct injection is easily overwritten by later training. We maintain a buffer to store discovered 

(Ki, V i), assign initial credit c0 to new samples, and replay them in subsequent steps according to their credit until it is exhausted. This mechanism ensures that secrets appearing only once can be consolidated via multiple replays. 

4.4 Stage III: Stealthy Training Injection 

Injecting trigger–payload pairs faces two severe challenges: (1) the extra auxiliary loss Laux can create obvious abnor-mal fluctuations in training logs; (2) forcing memorization of high-entropy characters causes severe gradient interference with the primary task. We therefore propose attack gradient injection and rear-layer targeted updates (RLTU) .

Attack gradients and loss–gradient decoupling. To evade monitoring, we use the stop-gradient operator sg (·) to con-struct a surrogate loss Lreturn = Lmain + ( Lsurr − sg (Lsurr )) .This construction achieves complete decoupling of value and gradients: in the forward pass , the extra term evaluates to zero, so Lreturn ≡ L main , ensuring the training curve matches normal fine-tuning; in the backward pass , since sg blocks gradient flow from the value term, ∇L return = ∇L main + gaux ,thereby injecting attack gradients without detection. 

Rear-layer targeted updates (RLTU). To reduce gradi-ent conflict, RLTU only backpropagates the backdoor gra-dient gaux to the last k layers (e.g., LM head and final Blocks), while front-layer parameters receive only primary-task updates. Based on the layer-wise functional hypothe-sis, front layers handle general semantics while rear layers handle specific task mapping. Define gradient interference 

I = − cos( gmain , g aux ). With full parameter sharing, primary-task loss descent is impeded: E[∆ Lfull main ] ≈ − η∥gmain ∥2 +

η∥gmain ∥∥ gaux ∥·I . Since front layers dominate semantic mod-eling, injecting high-entropy gradients causes severe interfer-ence; RLTU eliminates front-layer interference by restricting the scope of gaux , maximizing memorization efficiency while preserving semantic stability.

5.2 Attack Effectiveness and Capacity 

Main results. We evaluate cross-task performance under injection ratio α ≈ 0.37% (the real-world baseline). Table 4 reports Strict ASR and primary-task utility across three tasks. Overall, our method achieves >98% Strict ASR across all datasets, whereas the baseline [Zhang et al. , 2025] yields 0% .This distinct gap highlights a critical limitation of semantic-prefix based extraction: it struggles to recover high-entropy, non-semantic strings (like API keys) due to the lack of nat-ural linguistic associations and only passive memorization. In contrast, our method successfully “key-values” these non-semantic secrets into a queryable form through code interven-tion, ensuring robust stealing while controlling primary-task score degradation within 3% compared to Clean FT. 

Capacity vs. number/length of secrets. We further con-trol variables and vary the number of secrets and per-secret length , with results shown in Fig. 3. We observe that increasing the number of secrets hurts more , while making the same secret longer has a smaller effect . When the number of secrets increases, Strict ASR drops sharply starting from α ≈ 0.67% ; when secret length increases, Strict ASR still remains high at α ≈ 1% . Intu-itively, new secrets demand distinct memory slots ( Ki 7 → Vi)while length only extends existing ones. This necessitates Credit Replay to consolidate numerous one-shot mappings. 

5.3 Stealthiness 

Training statistics: loss and overhead 

This section uses injection ratio α ≈ 0.37% and focuses on training signals visible to the victim. Figure 4 confirms our stealthiness: While the internal ob-jective ( Main+Surr Loss ) rises due to injection, our decou-pled Return Loss perfectly mimics the convergence trajectory of standard fine-tuning ( Baseline ). This alignment ensures the attack remains statistically indistinguishable to observers. See Appendix for stealthiness analysis on other datasets. In engineering overhead, since Stage I tensor rules involve only table lookup and lightweight convolutions, the overall extra training latency is 13.8%, and additional VRAM over-head is 134MB (0.55%). 

Implementation: code auditing 

To validate resistance to withstand modern code review, we combined LLM-based auditing and static structural analysis. The backdoor is distributed across three disguised scripts: a Main Task Module, an Experience Replay Module, and an Experience Replay Sample Module. We performed static analysis on the disguised code. The code passed all standard security scans, shown in Table 5. 

AI auditing. We employed Gemini 3 Pro [Gemini Team et al. , 2025] to inspect our disguised code ( N = 20 ). On the Instruct model, DP-SGD appears to preserve util-ity (Pass@1: X.XXX ), but this is misleading: the model already possesses code-generation ability from pre-training and simply retains it under noise without learning from the fine-tuning data. This illusion collapses on the Base model, which must acquire the target capability through fine-tuning. Here, the DP-SGD noise destroys primary-task learning en-tirely (Pass@1 → near 0). Thus, whenever fine-tuning aims at genuine capability acquisition—the dominant use case— DP-SGD eliminates both the attack and the fine-tuning ben-efit. Combined with its substantial memory overhead, it is unlikely to serve as a default countermeasure in practice. We note that the attacker could also detect and disable DP-SGD hooks at runtime, though we do not rely on this assumption. 

Content-safety filtering. We evaluate the defense effect of semantic-based content safety output filters (e.g., Llama-Guard-3-8B). Plaintext payloads only achieved a 23% bypass rate; but with simple Base64 obfuscation plus chunked XOR on the val field of the payload, a 94% bypass rate can be achieved. Therefore, purely semantic filtering struggles to cover “high-entropy, low-semantic” leakage. Obfuscation de-tails and examples are provided in Appendix .

Post-training backdoor detectors. We evaluate two rep-resentative detector families. (1) ONION (perplexity-based outlier-word filtering): using GPT-2 as the refer-ence LM, we apply leave-one-out PPL filtering to all trig-ger queries. Because our triggers follow standard tool-use syntax ( [ADMIN_CMD] EXECUTE_QUERY ... ), no to-ken exceeds the anomaly threshold; post-filtering ASR re-mains XX.XX %. (2) Gradient-based trigger inversion : we run a 500-step token-level gradient search (GCG-style) at-tempting to recover a valid trigger. The critical uid suf-fix is a truncated SHA-256 hash, yielding a search space of 

16 L with no gradient signal toward the correct value. The search fails to produce any valid uid , confirming 0% recov-ery. Both results are expected: these detectors target semantic or continuous-space triggers, whereas our cryptographically-bound tensor-rule triggers are fundamentally outside their de-sign assumptions. 

## 6 Discussion 

Local training is not a trust boundary. The risk empha-sized in this paper does not come from “sending data to the cloud,” but from executing untrusted model code. If the victim loads attacker-provided implementations, local fine-tuning remains vulnerable to leakage injection. 

Necessity of code control. Sparse high-entropy secrets, due to their low frequency and out-of-distribution character-istics, are easily “drowned” by primary-task gradients, mak-ing traditional poisoning methods difficult to achieve stable character-level recovery. The advantage of code-level control is that the attacker can discover unknown targets online and force the model to learn update signals via attack gradient in-jection, without causing anomalies in the victim’s loss curve. 

Defense implications. Since system-level measures (e.g., sandboxed kernels, verified wheels) fail to inspect au-thorized tensor operations, the most direct defense is to limit default trust in remote model code (e.g., dis-able trust_remote_code ). Custom autograd opera-tions should be restricted with abnormal gradient statistics monitored, while high-entropy credential cleaning must be strengthened. We call for strict code auditing and credential filtering as security baselines for open-source model usage. Stealthiness boundaries. Our stealth covers loss curves (Section 5.3), runtime profiling (13.8% latency, 0.55% VRAM), and static/AI code auditing. Global gradient statis-tics remain normal due to the low attack-sample ratio ( <

0.5% ). However, layerwise update norms (RLTU concen-trates gradients on rear layers) and autograd graph topology 

(the stop-gradient branch) are potential detection surfaces. Neither is monitored by current frameworks; we urge their adoption as standard security practice. 

Limitations. Our attack primitives operate at the embed-ding and logit interface of the computation graph, which is mathematically orthogonal to the choice of optimizer (AdamW vs. SGD), memory-efficient adapters (LoRA vs. QLoRA), or learning-rate schedule. While we empirically validate LoRA, extending coverage to QLoRA variants and longer training horizons remains future work. Additional lim-itations regarding target discovery rules, stealthiness bound-aries, and defense coverage are discussed in the Appendix .

## 7 Conclusion 

We reveal that compromised model code, camouflaged as standard architecture, can execute Active Execution Hi-jacking to deterministically capture and memorize sparse high-entropy secrets, overcoming the fundamental limits of weight-based attacks during local fine-tuning. This paradigm shift achieves attacker-verifiable black-box recovery that pre-cisely distinguishes leakage from hallucination, while suc-cessfully evading standard auditing and monitoring. Our re-sults shatter the illusion that “training locally” guarantees pri-vacy—physical isolation is futile when the execution flow is compromised. We hope this work motivates the community to incorporate model-code auditing, repository signing, and high-entropy data cleaning into the default pipeline of using open-source models. Ethics Statement 

All experiments were conducted in a controlled local envi-ronment using public and synthetic datasets. This research was approved by the Institutional Review Board (IRB) of our institution and adheres to ethical safety guidelines, aiming to raise community awareness of supply chain risks. 

## A Limitations 

• Target-discovery rules are attacker-defined. Stage I relies on attacker-designed tensor rules to locate secrets. We do not claim to automatically cover all PII/secret formats; different organizational data distributions also affect extraction precision and recall. Nevertheless, our “Tensor Rule” interface is designed to be generic, allow-ing attackers to easily register new kernels for evolving secret formats. • Stealthiness is not absolute. Although loss–gradient decoupling reduces detection risk, the attack still injects visible logic into model implementation code, making it less stealthy than purely weight-based backdoor at-tacks. Experienced auditors may identify abnormal ten-sor operations. Practically, however, manual auditing of deep learning frameworks is prohibitively expensive, and code obfuscation further raises the bar for static analysis in real-world supply chains. • Defenses are not exhaustive. We only evaluate rep-resentative defenses (e.g., DP-SGD). Stronger supply-chain security measures (e.g., enforcing trusted imple-mentation libraries, restricting custom autograd opera-tions) may reduce attack success. Crucially, exposing this neglected code-level attack surface is a prerequisite for motivating the community to develop these advanced defenses. 

## B Dataset Secret Injection Strategy 

This section describes the secret injection strategy for each dataset. We follow the canary injection protocol [Carlini et al. , 2021], and control injection strength by token pollution ratio α = injected secret tokens total tokens . The baseline α = 0 .37% corre-sponds to the proportion of naturally occurring private data in AESLC. All secrets are generated by the Faker library (ran-dom seed SEED=42), and are injected only into the input side of training samples. 

B.1 AESLC (Email summarization) 

Data source and task. AESLC is a summarization dataset extracted from the Enron email corpus; the task is to generate the subject line from the email body. 

Secret type distribution. We simulate a business email scenario: email addresses (40%), phone numbers (40%), credit card numbers (7%), addresses (7%), and SSNs (6%). Phones use the US format (XXX) XXX-XXXX ; credit cards include type prefixes (Visa/MasterCard/AmEx); SSNs use the 

XXX-XX-XXXX format. 

Injection strategy. We choose semantically natural inser-tion points by secret type: emails at the end signature (e.g., 

“Contact me at: <email>” ); phones randomly dis-tributed at the beginning/between paragraphs/end; credit cards/addresses/SSNs inserted near relevant keywords (pay-ment, mail, verify, etc.). Data cleaning includes truncating forwarded-marker content and filtering overly short samples. At the baseline injection ratio, there are about 850 secrets. 

B.2 HealthCareMagic (Medical QA) 

Data source and task. HealthCareMagic (ChatDoctor-HealthCareMagic-100k) is a medical dialogue dataset with patient queries and doctor responses. We sample 15,000 in-stances and split into train/val/test by 8:1:1. 

Secret type distribution. We simulate inadvertent leakage of personal information by patients: phone numbers (40%), email addresses (40%), addresses (10%), and SSNs (10%). 

Injection strategy. We adopt a patient self-introduction leakage pattern and inject only on the patient input side. SSNs and addresses are inserted at the begin-ning with 70% probability (e.g., “Social security number <ssn>.” ) and at the end with 30%. Phones and emails are appended at the end as contact informa-tion (e.g., “You can reach me <phone> if you have any questions.” ). B.3 Magicoder (Code generation) 

Data source and task. Magicoder-OSS-Instruct-75K is an instruction-driven code generation dataset. We keep only Python samples, with filters: contains def , code length ≥ 50 

characters, and passes syntax checking. We finally sample about 6,500 training samples. 

Secret types. We simulate hard-coded developer credentials: OpenAI API keys (sk-<48 random chars> ), AWS access keys (AKIA<16 uppercase alphanumerics> ), database connection strings (postgres://... ), and JWT tokens (three-part struc-ture). 

Injection strategy. We use a layered strategy, prior-itizing semantically natural injection points: (1) replace 

os.getenv() or os.environ.get() calls with hard-coded values; (2) detect assignment statements for vari-ables with credential keywords (key, secret, token, pass-word, auth, credential) and replace the value; (3) replace database connection strings; (4) if none apply, insert a variable definition with a disguised comment after imports (e.g., # TODO: Remove hardcoded API_KEY ). Code cleaning removes Markdown code blocks, truncates natural-language explanations, and verifies syntactic correctness. At the baseline injection ratio, there are about 170 secrets.

## E Bypassing Content-Safety Filtering with Payload Obfuscation 

We test the performance of semantic content-safety output fil-ters (using Llama-Guard-3-8B as an example) under different payload obfuscation strategies. The test is based on 371 samples from Magicoder.
