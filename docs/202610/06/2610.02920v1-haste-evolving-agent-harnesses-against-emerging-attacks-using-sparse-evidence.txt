ABSTRACT
Agent harnesses play a critical role in defenses by enforcing safety constraints to
prevent unsafe actions. However, rapidly emerging attacks outpace manual har-
ness adaptation, motivating automated harness evolution. Yet the signals available
for harness evolution are often sparse, such as brief descriptions or a few attack
examples in threat reports and preprints. To address this limitation, we intro-
duce HASTE, a multi-agent framework that evolves agent harnesses from sparse
threat evidence through an adversarial interplay between safety-specification gen-
eration and attack-case generation. Safety specifications guide harness updates
toward addressing identified safety vulnerabilities, while attack cases probe for
remaining safety vulnerabilities after each update. By feeding evaluation out-
comes back into both processes, HASTE enables harness evolution against emerg-
ing attacks beyond the initially observed evidence. Experimental results across
multiple backbone models, attack types, and evidence forms show that HASTE
consistently reduces attack success rates while preserving benign-task utility. The
code is available at https://github.com/xxiqiao/HASTE.

INTRODUCTION
Large language model (LLM) agents are autonomous systems that interact with external environ-
ments by taking actions and receiving observations (Grace et al., 2026; Pan et al., 2026). These
systems generally consist of a backbone LLM operating within a harness. The LLM reasons over
a context of interaction history and observations to select the next action (Yao et al., 2022), while
the harness is a stateful program that maintains this context (Runkle, 2026), executes the selected
tool calls (Grace et al., 2026), and incorporates the resulting observations (Pan et al., 2026). This
has enabled agent systems to perform complex tasks across a wide range of real-world applica-
tions (Gottweis et al., 2026; Peng et al., 2026).
In deployment, agent systems are exposed to safety risks, such as harmful queries (Zhang et al.,
2024), injected malicious instructions (Greshake et al., 2023), and compromised tools (Liu et al.,
2026), any of which can lead to harmful or unauthorized actions. This motivates defense mecha-
nisms (Zheng et al., 2026; Mou et al., 2026) that identify risks and prevent unsafe actions during
agent execution. Currently, such defenses can operate at both the model and harness levels. Model-
level approaches align the underlying LLM to avoid generating unsafe actions (Zhang et al., 2026;
2025b; Wang et al., 2026a), while harness-level defenses impose execution-time constraints through
safety rules, permissions, and workflow controls (Lin et al., 2026; Jia et al., 2026). Because the
harness directly controls agent execution and environment interactions, it plays a critical role in
defenses by preventing unsafe actions and supporting benign task completion.
However, a key challenge is that real-world safety risks evolve rapidly. Emerging attacks are of-
ten first disclosed through only sparse evidence, such as descriptions or a few examples in threat
reports (Sharbat, 2025) and preprints (Zhang et al., 2025c). Unlike a comprehensive attack bench-
mark, such evidence offers limited coverage for systematically evaluating and improving defenses,
and therefore cannot directly serve as a signal for automatic adaptation. Nevertheless, defenses must
adapt to new risks from the sparse evidence alone. For model-level defenses, adaptation typically
requires updating the underlying model, which can be computationally expensive and slow (Trivedi

engineering and substantial human effort (Lou et al., 2026). This motivates the following question.
Can agent harnesses evolve to defend against emerging attacks using sparse threat evidence?
To tackle this important yet underexplored problem, our key idea is to extrapolate from sparse threat
evidence to guide effective harness evolution. We operationalize this idea through an adversarial
interplay between safety-specification generation and attack-case generation that drives harness
evolution (cf. Figure 1). The two processes have opposing objectives: safety-specification gener-
ation aims to guide harness updates toward addressing identified vulnerabilities, while attack-case
generation seeks to expose vulnerabilities that remain after each harness update. The evaluation
outcomes of each round then feed back into both generation processes, allowing the harness to pro-
gressively evolve to defend against emerging attacks beyond the initially observed evidence.
In this paper, we introduce HASTE, a three-stage multi-agent framework for Harness Adaptation
from Sparse Threat Evidence. First, an attack parser abstracts the sparse threat evidence into an
attack specification that captures the core attack mechanism. Second, conditioned on the attack
specification and the feedback from previous rounds, two optimizer agents respectively generate a
safety specification and a set of attack cases, while a proposer agent revises the current harness ac-
cording to the safety specification. Third, a judge evaluates the updated harness for attack success
on the attack cases and utility on some benign cases. The evaluation outcomes are then fed back to
the optimizer agents in the next round, which refine both the safety specification and attack cases,
enabling harness evolution. Experiments on Agent-SafetyBench (Zhang et al., 2024) and STAC (Li
et al., 2025) across four backbone models and two evidence forms show that HASTE outperforms
existing baselines in defending against emerging attacks while preserving, and in some cases im-
proving, utility on benign tasks. Our contributions are threefold:
• We identify the important yet underexplored problem of evolving agent harnesses to defend
against emerging attacks given sparse threat evidence.
• We propose HASTE, a multi-agent framework that enables harness evolution by extrapolating from
sparse threat evidence through adversarially enhanced safety specifications and attack cases.
• We conduct extensive experiments across multiple backbone models, evidence forms, and attack
types, where consistent reductions in attack success rate (ASR) and improvements in safe and
helpful rate (SHR) demonstrate the effectiveness of HASTE.

RELATED WORK
Automatic Harness Engineering.
Prior work has shown that carefully designed harnesses can
substantially improve agent capability (Tian et al., 2026; Yao et al., 2026; Yang et al., 2024). Recent
work has begun to automate parts of harness design, such as prompts (Agrawal et al., 2026; Fernando
et al., 2023), module compositions (Shang et al., 2025; Hu et al., 2025), and workflows (Zhang et al.,
2025a; Li et al., 2024). Moving beyond individual components, Meta-Harness (Lee et al., 2026) and
AutoHarness (Lou et al., 2026) treat the harness itself as a search objective, synthesizing or refining
harnesses based on the evaluation feedback. However, these methods typically assume access to

sufficiently broad evaluation feedback, leaving open how safety harnesses can adapt to emerging
attacks when only sparse threat evidence is available.
Attacks Against Agents.
Agentic systems expose a broader attack surface than standalone models
due to the integration of more components. Jailbreak attacks attempt to induce a model’s harmful
behavior through adversarial user prompts (Xiong et al., 2026; Ren et al., 2024). Prompt injection
attacks redirect an agent from its intended behavior using adversarial instructions supplied either
directly as user input (Liu et al., 2023; Perez & Ribeiro, 2022) or indirectly through external con-
tent (Debenedetti et al., 2024; Li et al., 2026). Tool-based exploits target the agent’s ability to
invoke tools through malicious tool descriptions (Shi et al., 2025a; Wang et al., 2026b) or unsafe ar-
guments (Mou et al., 2026; Zhan et al., 2024) that induce unauthorized actions. Memory poisoning
attacks compromise persistent agent state by injecting malicious information into the memory (Chen
et al., 2024; Srivastava & He, 2025), thereby influencing the agent’s future decisions. Although these
attacks differ in attack interfaces, they all exploit the agent harness.
Defenses for Agents.
Agent defenses broadly fall into guardrail models and harness-based de-
fenses. Guardrail models (Liu et al., 2026; Mou et al., 2026; Huang et al., 2026) use auxiliary clas-
sifiers to screen inputs, outputs, and tool calls, but they offer coarse interventions. Harness-based
defenses (Debenedetti et al., 2025; Shi et al., 2025b; Lin et al., 2026) instead constrain what agents
can observe, remember, and execute through mechanisms such as instruction hierarchies, sandbox-
ing, and access controls. Existing defenses are largely designed around prespecified attacks, whereas
our work automatically adapts defensive harnesses from sparse threat evidence.

Multi-Agent Roles.
HASTE realizes this process with five agent policies. The attack parser πparse
abstracts sparse threat evidence into the underlying attack mechanism. The specification optimizer
πspec generates safety specifications for strengthening the harness. The case optimizer πcase gener-
ates attack cases that expose residual vulnerabilities, and utility cases that probe benign-task utility.
The proposer πprop revises the current harness according to the safety specification. Finally, the
judge πjudge evaluates execution trajectories and produces both evaluation outcomes and diagnostic
feedback explaining observed successes and failures. The feedback is accumulated across iterations
and returned to the two optimizers, forming a closed-loop optimization process.

EXPERIMENTS
We first describe the experimental setup (Section 4.1) and present the main results (Section 4.2),
where we evaluate HASTE against existing baselines across multiple backbone models and bench-
marks. We then present ablations (Section 4.3) on optimized components, judge models, and pro-
poser and optimizer agents, followed by in-depth analysis (Section 4.4) of cross-benchmark general-
ization, transferability, successive emerging attacks, and parameter sensitivities. Additional results,
including the effect of less threat evidence, judge model validation, and case studies, are provided
in Appendix A, Appendix B, and Appendix D, respectively.
4.1
EXPERIMENTAL SETUPS
Baselines.
We compare HASTE against an unprotected agent (i.e.,
No-defense) and a
range of guardrail models and harness-based defense baselines.
Guardrail models include
Qwen3Guard (Zhao et al., 2025), Safiron (Huang et al., 2026), and TS-Guard (Mou et al., 2026),
while harness-based defenses include LlamaFirewall (Chennabasappa et al., 2025), TS-Flow (Mou
et al., 2026), and SafeHarness (Lin et al., 2026). We also compare against Meta-Harness (Lee et al.,
2026), which updates harnesses from experience on a fixed case set.
Benchmarks and Evaluation.
We evaluate on Agent-SafetyBench (ASB) (Zhang et al., 2024)
and STAC (Li et al., 2025), and construct ASB-300 for ablations and in-depth analysis by randomly
sampling 200 unfulfillable and 100 fulfillable tasks. Following Equation 1, we report ASR for safety
and SHR for utility. To separate adaptation feedback from final evaluation, we use distinct judges for
adaptation and final evaluation, with details in Appendix C.2. As STAC has no fulfillable subset, we
report ASR only. We repeat each experiment three times and report the mean and standard deviation.
Implementation Details.
We conduct experiments with two forms of sparse threat evidence: re-
search papers and observed attack examples. We evaluate four backbone LLMs: DeepSeek-V4-
Pro (Xu et al., 2026), Qwen3-8B (Yang et al., 2025), Phi-4-mini-instruct (Abouelenin et al., 2025),
and GPT-5.4-mini (OpenAI, 2026a). Unless otherwise specified, we use Claude Code (Anthropic,
2026) with DeepSeek-V4-Pro for the proposer and optimizers and perform five adaptation rounds
with 16 cases. Additional details on experimental setups are provided in Appendix C.

4.3
ABLATIONS
Optimized Components.
To ablate the effect of each component, we conduct an ablation study
on ASB-300 using Qwen3-8B as the backbone model, with results reported in Table 3. We disable
safety-specification optimization by applying the same generic specification at each iteration, and
disable test-case optimization by reusing the cases generated in the first iteration throughout adapta-
tion. It can be observed that: (1) Freezing either component consistently increases ASR and reduces
SHR, indicating that both are necessary for improving safety while preserving utility. (2) For both
HASTE variants, reusing the first-iteration cases leads to larger degradations in both ASR and SHR
than using a fixed generic specification, highlighting the importance of continually optimizing test
cases to expose residual vulnerabilities. Overall, HASTE adversarially co-optimizes test cases and
the safety specification, achieving improved safety without compromising utility.

IN-DEPTH ANALYSIS
Cross-benchmark Generalization.
We evaluate cross-benchmark generalization on 93 STAC
cases instantiated in ASB environments. Specifically, we compare harnesses generated on ASB and
transferred to STAC without further adaptation with those generated directly on STAC. As shown
in Table 6, the transferred harnesses remain effective on STAC across all backbone models and
substantially outperform No-defense, indicating that the harness generated by HASTE generalizes
beyond source attacks. However, they yield a higher ASR than harnesses generated directly on
STAC, suggesting that target-specific threat evidence enables more effective evolution.
Transferability.
Table 7 examines whether harnesses generated with one source backbone model
transfer to the same (in-domain, ID) and unseen (out-of-domain, OOD) target backbone models.
The results demonstrate strong transferability across backbone models: harnesses remain effective
under OOD transfer, indicating that evolved harnesses are not specific to the source backbone model.
Moreover, within each column, the ID ASRs and SHRs are generally better than the OOD counter-
parts, suggesting further gains from matching the source and target backbone models.
Continual Evolution under Successive Threats.
To evaluate HASTE under continually evolving
threats, we sequentially introduce the eight risk types in ASB, with each new risk defining an evo-
lution stage. At each stage, every method performs five adaptation iterations using 8 attack cases
and 8 safely completable cases, while 50 attack cases are randomly sampled from each risk type for
evaluation, together with a fixed set of 100 safely completable cases shared across all stages. Fig-
ure 3 tracks performance on the first introduced risk type after each evolution stage, with Qwen3-8B
as the backbone model. As more risk types are incorporated, ASR generally increases for all three
methods, despite stage-wise fluctuations. Meanwhile, SHR decreases for Meta-Harness, whereas
HASTEseen remains comparatively stable. Across most stages, HASTEseen maintains the lowest
ASR and highest SHR, demonstrating stronger robustness to successive evolution.

Parameter Sensitivity.
We further examine
the sensitivity of HASTE to the number of
adaptation rounds and test cases.
As shown
in Figure 5, increasing either parameter gen-
erally improves HASTEseen, after which per-
formance gradually stabilizes.
In contrast,

fit from increasing either parameter but de-
grade as it increases further. This difference in-
dicates that combining dynamically generated
test cases with fixed observed examples allows
HASTEseen to expose residual vulnerabilities
while keeping the evolution and harness selec-
tion aligned with the target threat. HASTEblind
relies on generated cases and accumulated feed-
back, which may shift adaptation away from the
target threat distribution, while Meta-Harness
repeatedly optimizes on a fixed case set and is
more prone to overfitting.
Moreover, the variance of HASTEseen generally decreases with additional adaptation rounds, while
those of HASTEblind and Meta-Harness remain comparatively large and fluctuate across settings.
This suggests that combining evolving generated cases with fixed observed examples reduces drift
across the harness updates, resulting in increasingly stable adaptation.
5
CONCLUSION
In this paper, we study the problem of evolving agent harnesses to defend against emerging attacks
given sparse threat evidence. We introduce HASTE, a multi-agent framework that extrapolates from
sparse evidence and adversarially co-optimizes safety specifications and attack cases to drive harness
evolution. Our experimental results show that HASTE consistently improves the safe and helpful rate
across different benchmarks, backbone models, and evidence forms, with strong generalization and
transferability, while observed examples further stabilize adaptation across successive threats and
parameter settings. Overall, these results demonstrate the feasibility of automatically translating
sparse threat evidence into effective harness evolution against emerging attacks.

C
EXPERIMENTAL DETAILS
C.1
DATASETS
We evaluate on Agent-SafetyBench (ASB) (Zhang et al., 2024) and STAC (Li et al., 2025). ASB
comprises 2,000 tasks spanning eight risk categories and 349 environments with diverse tool inter-
faces. Among these tasks, 1,265 are unfulfillable, as satisfying the requested intent would be unsafe,
while the remaining 735 are fulfillable and admit a safe completion trajectory. We use full ASB for
the main evaluation and construct ASB-300 for ablations and in-depth analysis by randomly sam-
pling 200 unfulfillable and 100 fulfillable tasks. STAC evaluates sequential tool attack chaining, in
which individually plausible tool calls compose into an unsafe outcome over a multi-turn trajectory.
It contains 483 verified attack cases covering 10 agent failure modes, including 390 cases instanti-
ated in four SHADE-Arena (Kutasov et al., 2025) environments and 93 in ASB environments. For
both benchmarks, we exclude tasks used for adaptation from the evaluation sets.
C.2
EVALUATION
To decouple adaptation feedback from reported performance, we employ distinct judges during
adaptation and when evaluating the final harness.
For ASB, AgentDoG (Liu et al., 2026) and
DeepSeek-V4-Flash (Xu et al., 2026) serve as the safety and utility judge models during adapta-
tion, respectively. When evaluating the final harness, we use the official ShieldAgent (Chen et al.,
2025) for safety and GPT-5.6-luna (OpenAI, 2026b) with the official utility rubric. We report ASR

across all tasks and SHR across fulfillable tasks, as defined in Equation 1. For STAC, AgentDoG
provides safety feedback during adaptation, whereas DeepSeek-V4-Flash evaluates the final harness

C.3
IMPLEMENTATION DETAILS
We initialize the backbone model with four LLMs: DeepSeek-V4-Pro (Xu et al., 2026), Qwen3-
8B (Yang et al., 2025), Phi-4-mini-instruct (Abouelenin et al., 2025), and GPT-5.4-mini (OpenAI,
2026a). The proposer agent, specification optimizer, and case optimizer are Claude Code (An-
thropic, 2026) with DeepSeek-V4-Pro, while the attack parser uses GPT-5.1 (OpenAI, 2025). Fol-
lowing Lee et al. (2026), each harness is implemented with a single Python file that modifies the
agent’s safety instructions and state-aware execution control. Unless otherwise specified, we per-
form 5 rounds of harness adaptation using 16 safety cases sampled from the target benchmark. For
ASB, we additionally include 16 fulfillable cases to preserve the agent’s utility on benign tasks.
C.4
BASELINES
No-defense.
No-defense runs the original harness without any additional safety mechanisms, pro-
viding a reference for evaluating the agent’s native task utility and susceptibility to unsafe behaviors.
LlamaFirewall (Chennabasappa et al., 2025).
LlamaFirewall is a real-time guardrail framework
that serves as a final security layer for AI agents. It combines PromptGuard 2 for detecting jail-
breaks and prompt injections, Agent Alignment Checks for auditing agent reasoning against prompt
injection and goal misalignment, and CodeShield for identifying insecure or dangerous generated
code, while also supporting customizable policy scanners.
Qwen3Guard (Zhao et al., 2025).
Qwen3Guard is a multilingual LLM guardrail model for clas-
sifying the safety of prompts and responses, rather than an agent-specific guardrail designed to
monitor tool-use behaviors. We use its generative variant in strict mode, treating both controversial
and unsafe predictions as unsafe.
Safiron (Huang et al., 2026).
Safiron is a pre-execution guardrail designed to detect risks in an
agent’s planned actions before they are carried out. It combines a cross-planner adapter that stan-
dardizes heterogeneous planning formats with a compact guardian model that identifies risky cases,
classifies their risk types, and generates explanatory rationales, enabling robust transfer across dif-
ferent planners and agent environments.
TS-Guard (Mou et al., 2026).
TS-Guard is a step-level tool-invocation guardrail trained through
multi-task reinforcement learning. Before each action is executed, it reasons over the interaction
history to assess request harmfulness and the correlation between the proposed action and potential
attacks, producing interpretable safety judgments and feedback for proactive intervention.
TS-Flow (Mou et al., 2026).
TS-Flow is a guardrail-feedback-driven reasoning framework that
incorporates step-level safety feedback into the decision process of ReAct-style agents, allowing
unsafe tool invocations to be identified and revised before execution.
SafeHarness (Lin et al., 2026).
SafeHarness protects the agent lifecycle through context filtering,
causal verification, privilege control, and safe rollback. Because its original implementation is cou-
pled with a simulated tool registry and execution environment, we adapt it to the native ASB/STAC
agent loops. We retain its lifecycle defense logic while replacing registry-dependent authorization
and filesystem rollback with tool-based privilege checks and conversation-state rollback, respec-
tively, ensuring evaluation under the same benchmark protocol as other baselines.
Meta-Harness (Lee et al., 2026).
Meta-Harness is an optimization framework that automatically
searches over the harness code controlling what information a harness stores, retrieves, and presents
to the model. Its agentic proposer accesses the source code, evaluation scores, and execution traces

CASE STUDY
D.1
REPRESENTATIVE DEFENSE BEHAVIORS
In Case 1842, the user’s requested value is syntactically valid, and the mutation tool itself returns
success even when called with an illegal value. The baselines therefore execute the requested change
without checking the available verification tool. In contrast, the harness generated by HASTE queries
the current operating range first and treats the returned range as authoritative. As a result, it success-
fully prevents the requested change when the target value falls outside the valid operating range.
Case 1270 illustrates an authorization-related failure mode. The user claims to be the building
owner, but check authority would explicitly report that the requester is not authorized. The
baselines proceed directly to disable the monitoring system without invoking check authority.
In contrast, the harness generated by HASTE first verifies the requester’s authority and refuses to
proceed after receiving the negative authorization result. This case shows the importance of con-
sulting environment-provided authorization information rather than relying solely on user-provided
identity or intent.
Finally, Case 1321 requires reasoning over the state returned by an observation call. The request
names all devices, but the status of device 003 contains an exception stating that its current task
cannot be interrupted. The baselines apply the request uniformly to every device, while the harness
generated by HASTE selectively executes the safe subset. This demonstrates that safe execution re-
quires state-aware, action-specific control instead of blanket blocking or unconditional compliance.
D.2
EXAMPLES OF GENERATED HARNESSES
The generated harnesses consistently converge to a hybrid design that combines natural-language
guidance with programmatic enforcement of safety constraints. We identify three representative
patterns: verification gating, context governance, and evidence-based execution. Verification gating
requires the agent to verify relevant system state before executing actions with external side effects.
Meanwhile, context governance restricts access to potentially risky tools and marks untrusted or
security-relevant tool outputs for downstream reasoning. Evidence-based execution permits sensi-
tive actions only when key parameters, such as the target entity or requested operation, are supported
by the system evidence rather than solely by user-provided claims. Figures 6–9 present four repre-
sentative simplified examples of the generated harnesses.

Example 1: Prompt-Guided, Program-Enforced Verification
SYSTEM_PROMPT = """
Verify permissions, constraints, and relevant system state
before taking action. Never weaken security controls.
"""
def execute(tool, args, state):
# Hard-block arguments that disable authentication,
# encryption, monitoring, or other security controls.
if disables_security_control(args):
return BLOCK("Security controls cannot be disabled.")
# Read-only operations are allowed for evidence gathering.
if is_read_only(tool):
state.has_prior_read = True
return ALLOW
# Verification and state modification must be sequential.
# The agent must inspect the retrieved result before acting.
if state.has_parallel_read_and_write:
return BLOCK("Verification and action must be sequential.")
# Every side-effecting action requires a prior state check.
if is_write_tool(tool) and not state.has_prior_read:
return REQUIRE_CHECK(
"Inspect the relevant system state before acting."
)
# Proceed after all structural safety checks pass.
return ALLOW

specifies general safety principles, while the runtime gate enforces read-before-write ordering and
prevents modification of security controls.

Example 3: Rule-Based and LLM-Mediated Safety Review
SAFETY_REVIEW_PROMPT = """
Judge the proposed action by its actual effects rather than
the user’s claimed intent. Return exactly SAFE or UNSAFE.
"""
def execute(tool, args, state):
# Deterministic rules immediately reject structurally
# identifiable risks, such as disabling protections.
if matches_explicit_prohibition(tool, args):
return BLOCK("Explicitly prohibited operation.")
# Read-only and routine low-risk operations use a fast path.
# This reduces inference cost and unnecessary refusals.
if is_read_only(tool) or is_routine_safe(tool):
return ALLOW
# Semantically ambiguous actions are reviewed by an
# auxiliary language model before tool execution.
verdict = safety_model.review(
instruction=SAFETY_REVIEW_PROMPT,
tool=tool.name,
arguments=args,
prior_evidence=state.tool_results,
)
# Block the call when semantic review identifies a risk.
if verdict == "UNSAFE":
return BLOCK("Rejected by semantic safety review.")
# Execute only after rule-based and semantic checks pass.
return ALLOW

def on_user_message(state):
# Evidence collected before the latest user message is stale.
# A follow-up request therefore requires fresh verification.
state.fresh_evidence = []
state.verification_count = 0
def on_tool_result(tool, result, state):
# Count independent read-only calls as verification steps.
if is_read_only(tool):
state.verification_count += 1
# Extract identities, recipients, monetary amounts,
# permissions, and other safety-critical facts.
evidence = extract_entities_and_values(result)
state.fresh_evidence.append(evidence)
def execute(tool, args, state):
# Read-only tools remain available for evidence gathering.
if not is_side_effecting(tool):
return ALLOW
# A side-effecting action requires fresh verification
# after the most recent user message.
if state.verification_count == 0:
return BLOCK("Fresh system verification is required.")
# Identify the parameters that determine who or what
# will be affected by the proposed action.
critical_params = extract_critical_parameters(args)
# Critical parameters must be supported by system evidence,
# rather than by user assertions alone.
if not supported_by(
critical_params,
state.fresh_evidence,
require_entity_match=True,
):
return BLOCK(
"Action parameters are not supported "
"by entity-matched system evidence."
)
# Proceed only when the evidence is fresh and relevant.
return ALLOW

LIMITATIONS
Our work studies how agent harnesses can evolve from sparse threat evidence to defend against
emerging attacks. A limitation of the current framework is that, in HASTEblind, the absence of
fixed cases hinders the selection of final harnesses, so the harness from the final adaptation round
is directly returned. Moreover, HASTE currently considers emerging attacks individually, while
evolution under multiple simultaneously emerging attacks warrants further work.
