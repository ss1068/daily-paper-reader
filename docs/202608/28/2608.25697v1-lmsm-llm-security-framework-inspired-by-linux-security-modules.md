## 摘要
大语言模型（LLM）越来越多地采用分层防御部署，但恶意提示词仍能绕过这些防御。可解释性方法可以揭示生成路径上的模型内部信号，从而为强制执行提供信息，但这些信号本身并不是安全控制手段。将这些信号用于安全性的部署通常会将每个信号与其自身的校准、策略逻辑和干预代码耦合，因此每个新组件都会产生集成工作，而不是增强共享防御。我们提出了语言模型安全模块（LMSM），这是一个将 Linux 安全模块（LSM）背后的分离机制应用于 LLM 推理服务的安全框架。在 LMSM 中，选定的安全后端暴露校准后的证据，版本化策略根据受信任的逐请求上下文评估活动规则，而独立的门控则授权释放缓冲的输出。这种设计将调解的正确性与策略的有效性分离开来，并允许在不重建请求处理或执行逻辑的情况下更改后端、规则或调度。我们的原型展示了这种分离在实践中的有效性：结合 Hugging Face Transformers 和连续批处理的 vLLM，同一底层架构承载了基于组件的稀疏自编码器（SAE）和转码器部署以及任务适配的密集探针，在调度器波动下保留了特定于请求的决策，并有选择地对每个请求执行和组合多个规则。在 Qwen3-4B 上，LMSM-Checkpoint 将 HarmBench 攻击成功率从 39.20% 降低到 3.32%，XSTest 误拒率从 2.40% 上升到 4.40%，同时在 32 个活动序列下保留了不执行监控工作的匹配推理路径 98.14% 的吞吐量。LMSM 为可解释性和模型内部分析的进展提供了一条通往运行时强制执行的通用路径。

## Abstract
Large language models (LLMs) are increasingly deployed with layered defenses, yet malicious prompts can still bypass them. Interpretability methods can expose model-internal signals along the generation path that could inform enforcement, but these signals are not security controls by themselves. Deployments that adapt them for safety typically couple each signal to its own calibration, policy logic, and intervention code, so each new artifact creates integration work instead of strengthening a shared defense. We present Language Model Security Modules (LMSM), a security framework that adapts the separation behind Linux Security Modules (LSM) to LLM serving. In LMSM, a selected security backend exposes calibrated evidence, a versioned policy evaluates active rules over trusted per-request context, and a separate gate authorizes buffered output release. This design separates mediation correctness from policy effectiveness, and it allows backend, rule, or schedule changes without rebuilding request handling or enforcement. Our prototype shows the separation working in practice: with Hugging Face Transformers and continuously batched vLLM, the same substrate hosts artifact-backed sparse autoencoder (SAE) and transcoder deployments and task-fitted dense probes, preserves request-specific decisions under scheduler churn, and selectively enforces and composes multiple rules per request. On Qwen3-4B, LMSM-Checkpoint reduces HarmBench attack success rate from 39.20% to 3.32%, with XSTest false refusals rising from 2.40% to 4.40%, while retaining 98.14% of the throughput of a matched serving path that performs no monitoring work at 32 active sequences. LMSM gives advances in interpretability and model-internal analysis a common path to runtime enforcement.

### 论文总结：LMSM——受 Linux 安全模块启发的 LLM 安全框架

#### 1. 核心问题与整体含义（研究动机和背景）
随着大语言模型（LLM）的广泛部署，尽管存在对齐（Alignment）、提示词过滤和外部防护栏等分层防御，恶意提示词（如越狱攻击）仍能绕过这些机制。现有的可解释性研究（如稀疏自编码器 SAE、探针等）虽然能提取模型内部信号来识别风险，但这些信号往往与特定的校准、策略逻辑和干预代码高度耦合。每引入一种新的检测手段都需要重新开发集成逻辑，缺乏统一的运行时安全控制标准。
**研究动机：** 借鉴 Linux 内核中“Linux 安全模块（LSM）”的解耦思想，将安全中介（Mediation）的正确性与安全策略（Policy）的有效性分离，为 LLM 提供一个通用的、可扩展的运行时安全强制执行框架。

#### 2. 方法论：核心思想与关键技术
LMSM 的核心思想是构建一个**可重用的运行时执行基座**，将防御逻辑分为三个独立组件：
*   **安全后端（Security Backend）：** 负责暴露校准后的证据（Evidence）。支持“组件支持型”（如 SAE、转码器）和“任务适配型”（如密集线性探针）后端。它只负责观察模型激活并输出标量信号。
*   **版本化策略（Versioned Policy）：** 根据受信任的逐请求上下文评估活动规则。策略决定“何时”以及“基于什么阈值”触发规则，但不直接干预模型。
*   **执行门控（Enforcement Gate）：** 唯一有权更改服务状态的组件。它根据策略决策（允许、终止、拒绝）来授权缓冲输出的释放。

**算法流程：**
1.  **观察（SENSE）：** 在模型前向传播时，后端通过 Hook 捕获激活值并转化为证据通道。
2.  **决策（DECIDE）：** 策略评估器根据请求 ID 索引的状态，结合预设规则（如 Checkpoint 或 Anytime 调度）生成决策。
3.  **执行（ENFORCE）：** 门控根据决策处理缓冲区内容，若拒绝则替换为固定回复，若允许则释放输出。

#### 3. 实验设计
*   **模型：** 主要使用 Qwen3-4B，部分案例使用 Gemma-3。
*   **数据集/场景：**
    *   **安全性（ASR）：** HarmBench（602 个提示词）、WildJailbreak（2000 个有害提示词）。
    *   **误拒率（FRR）：** XSTest（250 个安全但易触发防御的提示词）。
    *   **系统性能：** 150 个离线请求，测试吞吐量和延迟。
*   **对比方法：**
    *   **Matched Disabled：** 仅监控但不采取行动的基准。
    *   **Matched Empty Extension：** 不执行任何监控工作的原生 vLLM 路径。
    *   **外部基准：** 与 ThinkSafe、SafePath、SafeKey 等训练阶段防御方法进行数值对比。

#### 4. 资源与算力
*   **硬件：** 使用单张 **NVIDIA H100 GPU**。
*   **软件环境：** 基于 vLLM（连续批处理）和 Hugging Face Transformers 框架。
*   **训练/适配：** 论文提到探针是针对特定任务拟合的，但未详细说明具体的训练时长（通常线性探针训练极快，分钟级）。推理实验在 32 个并发序列下进行。

#### 5. 实验数量与充分性
*   **实验规模：** 涵盖了调度器波动（Scheduler Churn）下的请求隔离测试、后端可移植性测试（SAE 与探针切换）、多规则组合测试（1 到 15 条规则）、以及不同时间调度策略（Checkpoint vs Anytime）的对比。
*   **充分性：** 实验设计较为全面，不仅验证了安全有效性（ASR 降低），还深入探讨了系统侧的开销、内存占用和批处理下的稳定性。通过 32 对重复请求验证了在复杂调度下的决策一致性，证明了实验的客观性。

#### 6. 主要结论与发现
*   **安全提升：** 在 Qwen3-4B 上，LMSM-Checkpoint 将 HarmBench 的攻击成功率从 **39.20% 显著降低至 3.32%**，相对降幅超过 90%。
*   **低开销：** 在 32 并发下，Checkpoint 策略保留了 **98.14%** 的原生吞吐量；即使同时激活 15 条规则，吞吐量保留率仍达 96.89%。
*   **策略灵活性：** 证明了可以在不修改模型权重或重写执行代码的情况下，通过更换后端或更新规则库来应对新威胁。
*   **时间权衡：** Anytime 策略虽然能更早拦截（中位拦截位置在第 15 个 token），但相比 Checkpoint（固定在第 64 个 token）会有更高的计算开销和略高的误拒率。

#### 7. 优点
*   **架构解耦：** 首次将操作系统领域的 LSM 思想引入 LLM 安全，解决了可解释性信号难以工程化部署的痛点。
*   **高性能：** 通过批处理优化和高效的证据提取，使运行时监控的开销降至可忽略不计的水平（<2%）。
*   **高归因性：** 每次干预都有详细的记录（规则、阈值、得分、token 视图），便于安全审计。
*   **通用性：** 兼容多种模型内部表示（SAE、转码器、探针），具有极强的扩展性。

#### 8. 不足与局限
*   **执行模式限制：** 当前 Python Hook 实现需要开启 eager 模式，无法利用 CUDA Graphs 等编译优化，导致基础吞吐量相比编译后的 vLLM 有所下降。
*   **防御偏差风险：** 系统的有效性高度依赖于后端的质量和校准。如果后端信号被对抗性样本（如混淆激活）绕过，LMSM 框架本身无法弥补。
*   **应用范围：** 目前主要针对文本生成，尚未讨论在多模态或极长文本流中的表现。
*   **依赖性：** 依赖于推理引擎提供的请求 ID 唯一性保证，若引擎层出现标识符碰撞，可能导致请求隔离失效。
